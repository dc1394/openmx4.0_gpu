Single-node cooperative dense GEMM
=================================

Implementation: source/openmx_mgpu_gemm.cu and openmx_mgpu_gemm.h.
The application runtime admits operations from the main collinear and
noncollinear cluster solvers and ordinary Band solvers selected with
scf.eigen.lib=gpusolver or gpusolver3. Band operations
select one equal GPU group per computed k-point (see band_mgpu.txt).
Node topology, input enablement, GPU selection,
size thresholds and interprocess locking belong to openmx_mgpu_runtime.cu.
The numerical core has no MPI calls and accepts an explicit list of CUDA-visible
device ordinals. Devices with the same PCI bus ID are rejected: two MIG instances
on the same physical GPU do not count as two cooperating GPUs.

Algorithm and numerical behavior
-------------------------------

Partition the output into row/column tiles and assign one tile to each GPU in a
wave. Every tile retains the complete K dimension. There is no split-K reduction
and no new reduced-precision arithmetic. Copy raw operand submatrices with their
storage orientation intact; the local GEMM applies N, T or C. This supports real
and complex GEMM, rectangular back transforms, padded leading dimensions, host or
device alpha/beta, and the two products H X followed by X^T H X or X^H H X.
The two forward products are separate calls; their intermediate matrix returns
to the source GPU. A worker caches its current operand tiles within one call.
For CUDA host operands, the traversal compares the bytes required by row-first
and column-first assignment, including reuse on each worker and partial edge
tiles. It chooses the smaller transfer volume without changing tile budgets,
the complete K dimension, or the arithmetic within each output tile.

Each worker owns a nondefault stream and cuBLAS handle. Peer copies and GEMMs are
queued on these streams; all workers queue their GEMMs before a host-staged gather
waits. CUDA workers also queue all pinned host-result downloads before waiting
on the first device. Completed tiles are scattered into the private transaction
while the remaining devices can continue their downloads. Input readiness comes
from an event on the caller's stream. Where peer
access is unavailable or cannot be enabled, bounded portable pinned buffers
stage transfers through host memory. OPENMX_MGPU_GEMM_FORCE_HOST=1 exercises this
route even on NVLink systems. Peer enablement is cached per directed device pair.

When linked into OpenMX, workers call the existing real/complex GEMMul8 bridge.
Its input/environment arithmetic choices therefore remain effective: GeForce
workers can retain accurate Ozaki, and strong-FP64 devices use their general-GEMM
policy. OPENMX_MGPU_GEMM_BACKEND=native explicitly chooses local cuBLAS instead.
Standalone builds without the weak bridge symbols also use native cuBLAS.
The in-worker guard prevents recursive multi-GPU dispatch. Explicit forward
precision stages are propagated to worker tiles. Their prepared-X cache is
not reused after a tile upload; original single-device prepared-X reuse is
unchanged. Full-K tiles keep the requested precision and scaling policy.

Success waits for all results and restores the caller's current CUDA device.
It does not modify the caller's handle, stream, pointer mode, math mode or atomics
mode. This first implementation offers concurrency among worker GPUs but is
synchronous at the public API boundary.

Memory and fallback contract
----------------------------

All results first land in a contiguous private transaction buffer. It resides
on the source GPU when the configured device budget and free memory allow both
the result and a worker tile. Otherwise it resides in host memory, with bounded
pinned staging for completed tiles. No extra full matrix on the owner GPU is
required merely to enable cooperation. OPENMX_MGPU_GEMM_RESULT_HOST=1 forces
the host transaction for validation.
Only after every worker and gather succeeds is the result copied into user C,
preserving its leading-dimension padding. A recoverable allocation, transport or
worker failure before this commit returns 0 with C unchanged, so the caller can
execute the original single-GPU GEMM, including nonzero beta. A commit or CUDA
synchronization failure is returned as handled with an error status; callers
must not retry that operation blindly. Unsupported graph capture, invalid device
lists and insufficient full-K budgets also decline before committing C.

Environment variable                         Default  Meaning
OPENMX_MGPU_GEMM_WORKSPACE_MB                 1024     A+B+C tile buffers per GPU
OPENMX_MGPU_GEMM_RESULT_MB                    2048     Full source-GPU result cap
OPENMX_MGPU_GEMM_HOST_RESULT_MB              65536     Host result cap
OPENMX_MGPU_GEMM_RESULT_HOST                    0     Force a host result buffer
OPENMX_MGPU_GEMM_HOST_MB                       256     Pinned staging per worker
OPENMX_MGPU_GEMM_RESERVE_MB                    512     Free device-memory reserve
OPENMX_MGPU_GEMM_FORCE_HOST                     0     Force host-staged transport
OPENMX_MGPU_GEMM_BACKEND                   bridge     bridge or native arithmetic
OPENMX_MGPU_GEMM_ASYNC_GATHER                   1     Queue CUDA host-result downloads together
OPENMX_MGPU_GEMM_TRAVERSAL                   auto     CUDA host tiles: auto, row, column

Byte caps use MiB (1024^2 bytes). Zero workspace/host budgets disable the
corresponding allocation. A zero device-result budget selects host results;
setting both result budgets to zero declines the operation. Zero reserve removes
that reserve. The backend checks
OpenMX's physical free-memory helper when linked, otherwise cudaMemGetInfo.
The source GPU can hold both its worker buffers and the transaction buffer.
CUDA contexts, cuBLAS internals and the existing bridge's own bounded workspace
are additional allocations. All operand/result/pinned scratch is freed before
return. Handles and streams are cached per host thread, with explicit cleanup
through openmx_mgpuGemmRelease().

Core API and diagnostics
-----------------------

openmx_mgpuDgemmTry / openmx_mgpuZgemmTry take the ordinary cuBLAS GEMM arguments
plus ngpu, a device-ordinal array and an output status pointer. A return of 0
means decline and untouched C. A return of 1 means handled; inspect the status.
They can be called directly while the application already owns its operation
lock. openmx_mgpuGemmInWorker() identifies recursive bridge calls.

openmx_mgpuGemmLastReport() copies a host-thread-local report with requested and
active GPU counts, output tiles, bridge calls, peer/host transfer counts,
transaction bytes, per-worker bytes, total wall time and a static reason string.
The active count records GPUs that actually enqueued a product, not merely
devices that were discovered. The transfer counts refer to remote transfers;
copies local to the source GPU are excluded.

Tests and benchmarks
--------------------

CPU arithmetic/indexing and failure tests:
  python3 tests/run_mgpu_gemm_cpu.py
This compiles the production core against fake CUDA devices and runs the same
numerical fixture for 2 and 4 devices. GPU stream/transport validation is separate.

Build on a GPU-less login node (site CUDA/toolchain example):
  CUDA_HOME=/home/app/hpc_sdk/Linux_x86_64/24.7/cuda/12.5 \
  CUDA_MATH_ROOT=/home/app/hpc_sdk/Linux_x86_64/24.7/math_libs/12.5 \
  NVCC_HOST=/opt/gcc/12.2.0/bin/g++ \
  HOST_LIBDIR=/opt/gcc/12.2.0/snos/lib64 GPU_ARCH=80 \
  sh tests/run_mgpu_gemm_smoke.sh source/build/mgpu-tests --build-only

Run inside an allocated node with at least two physical GPUs:
  source/build/mgpu-tests/mgpu_gemm_smoke --ngpu 2
  compute-sanitizer --tool memcheck --error-exitcode 99 \
    source/build/mgpu-tests/mgpu_gemm_smoke --ngpu 2
Use --ngpu 4 for four GPUs. The fixture covers real/complex N/T/C,
alpha/beta, device scalars, NaN C with beta zero, padding, nondefault streams,
long K, bounded tiling, both forward pairs, rectangular back shapes, peer/host
paths, row/column/automatic host tile traversal, a nonzero source device,
and transactional rollback after a later worker
rejects its tile. Numerical references use independent long-double sums.
The default smoke uses a lightweight bridge wrapper to test recursion; it is
not a numerical test of the external GEMMul8 kernels.

Native one-GPU versus cooperative GEMM, with all transfers/allocations included:
  source/build/mgpu-tests/mgpu_gemm_bench --ngpu 2 \
    --m 8192 --n 8192 --k 8192 --iterations 10 --forward
Add --complex for Z. Omit --forward for a single N/N product and use independent
--m/--n/--k dimensions. Repeat --ngpu 4 on a four-GPU allocation. CSV output
reports wall time, relative error against the single-GPU output, active GPUs,
transport counts and scratch bytes. A decline or wrong active count fails the
benchmark instead of silently timing a single-GPU fallback.

Add --host to measure the host-backed capacity path against a single GPU
with host operands/results. Both paths include uploads and downloads; the
native baseline retains preallocated device scratch. The cooperative warm-up
registers bounded pinned buffers, which subsequent products reuse inside one
staging scope. Use OPENMX_MGPU_GEMM_ASYNC_GATHER=0/1 on the same executable
to compare the sequential and overlapped gathers without changing arithmetic,
GPU counts or tile budgets. The standalone CUDA builds enable host OpenMP,
matching the production packing/scattering loops. Set OMP_NUM_THREADS and
bind the process to the corresponding CPU cores when measuring them.
Use OPENMX_MGPU_GEMM_TRAVERSAL=row/column/auto to compare tile assignment;
row retains the previous traversal. Device-operand and HIP calls keep their
existing row-first assignment.

For the retained production single-GPU arithmetic policy, build the same source
with the actual bridge and an existing GEMMul8 template object:
  GEMMUL8_TEST_OBJECT=/absolute/path/to/gemmul8_openmx.o \
    sh tests/build_mgpu_gemm_bridge_bench.sh source/build/mgpu-tests
Use the same CUDA/toolchain variables as above. The resulting executable is
mgpu_gemm_bench_bridge, with the same options. Its forward baseline invokes
actual Fixed GEMMs and trims scratch after each pair, including A100's accurate
Ozaki policy for sufficiently large real square matrices. Its workers also use
the actual bridge. This comparison is necessary before changing automatic
thresholds: a speedup over native cuBLAS alone need not beat retained Ozaki.

Application regression (run in a single-node GPU allocation with MPI/MPS set up
by the caller):
  python3 tests/run_mgpu_cluster_regression.py \
    --baseline /absolute/path/to/pre-mgpu/openmx --binary source/openmx \
    --output /new/private/result/directory --ranks 2 --gpus 2
Use --ranks 4 --gpus 4 on a four-GPU node. --prepare-only writes the inputs and
binary snapshots without launching MPI. The output directory must not exist.
Defaults run Pt63 collinear off, collinear on and noncollinear SOC for exactly
three SCF steps each, against disabled, forced MAGMA and automatic
solver modes. Both spin-polarized variants start with populations 8.5/7.5 per Pt;
the noncollinear rows add 45 15 45 15 1. The template and existing outputs are
untouched. Absolute DATA.PATH and private binary hashes are recorded.

The runner forces both Cluster GPU thresholds and multi-GPU GEMM eligibility so
these relatively small matrices test the implementation rather than the speed
threshold. It checks finite energy components and all 189 force components,
with default total-energy/maximum-force tolerances of 1e-7 Ha and 1e-7 Ha/bohr.
Successful enabled cases must log GEMM with the expected real/complex type and
the requested active GPU count. Forced eigensolver cases must also record that
backend, so a silent fallback cannot pass. Automatic solver selection may choose
single-GPU. Every planned run, output, backend record and numerical difference
is preserved in command.json, results.json, comparisons.json and summary.json.

---------------------------------------------

measurements use ten timed repetitions after warmup; 3-GPU square forward

transfers, arithmetic and final commit.

The current default distributes all eligible nonempty GEMMs in the permitted
solver group, including skinny outputs and PCIe-only GPUs. Explicit
OPENMX_MGPU_GEMM=0 disables device-operand cooperation. The optional legacy
OPENMX_MGPU_GEMM=auto policy requires max(M,N)>=8192, min(M,N)>=4096,
K>=8192 and direct bidirectional NVLink/P2P. OPENMX_MGPU_GEMM_MIN_N overrides
the size floor (default 1, or 8192 in legacy auto mode); the smaller output
floor is its rounded-up half. OPENMX_MGPU_GEMM=1 bypasses these optional gates.
The earlier measurements above explain why legacy auto can be faster for
small or narrow matrices: distributing a kernel does not guarantee speedup.
Three GPUs did not improve real forward time over the separate two-GPU runs;
GPU count is a user limit, not a claim that every extra GPU improves speed.

Numerical/transport validation: all 64 smoke cases passed on both two and three
physical A100 GPUs, maximum error 1.435e-14 versus independent long-double sums.
Two-GPU compute-sanitizer memcheck reported zero errors after caching directed
peer enablement. Integrated forward comparisons above had maximum relative
difference 1.115e-13 from retained single-GPU arithmetic. Forced accurate Ozaki
workers also passed real/complex n=1024 checks, although small forced operations
were slower. Physical GeForce and four-GPU runs have not yet been measured.

Host-backed capacity products
-----------------------------
openmx_mgpuDgemmHostTry / ZgemmHostTry use the same full-K tile algorithm
with host operands and a host transaction buffer. A and B tiles are packed
into bounded pinned buffers and uploaded to the assigned worker. Completed
C tiles return to the host transaction; the caller's C is committed only
after every tile succeeds. No full owner GPU result allocation is made.
The independent host result cap is OPENMX_MGPU_GEMM_HOST_RESULT_MB (65536
MiB); the existing worker and pinned budgets still bound GPU/tile storage.
These calls serve forced MAGMA and automatic memory recovery regardless of
the optional performance GEMM toggle. Recoverable capacity failures leave C
unchanged and the runtime uses CPU BLAS. Execution or publication failures
remain errors, since retrying a partially published result is unsafe.
