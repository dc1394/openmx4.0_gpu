Local capacity GEMM optimization
--------------------------------
CUDA host-backed products now choose row-first or column-first output tiles
according to the bytes uploaded with the existing per-worker A/B cache.
Partial tiles and the round-robin worker assignment are included. Full K,
tile budgets, FP64 arithmetic and transactional publication are unchanged.
Pinned output downloads are enqueued on all workers before the completion
loop scatters them into the private host result. Device-resident calls and
HIP keep their existing traversal.

PBS 943389, two allocated GPUs, 8 CPU threads, n=8192, H X then X^H H X
(real uses transpose), host operands/results, five timed repetitions after
warm-up per process, two process samples per setting:

                            real (ms)     complex (ms)
  old gather + row           1795.900        4828.537
  async gather + row         1788.886        4821.293
  async gather + auto         1468.020        3519.913
  old/new speedup                1.223           1.372

The isolated gather difference is within measurement noise. The traversal
change accounts for the observed gain. The single-GPU host bridge takes

results do not justify spreading fitting single-GPU work over more GPUs.
The capacity-first default is preserved. The native benchmark preallocates
its device scratch; cooperative timings include per-call worker allocation.
Both timed paths include host transfers. No extra memory budget was granted.

Low-memory recovery and bounded packing
---------------------------------------
PBS 943417, two A100 GPUs, Si64 Cluster collinear/noncollinear, two MPI
ranks and eight threads each. A test-only LD_PRELOAD interposer caps reported
free GPU memory at 280 MiB after the process creates its first cuSOLVER
handle. This leaves only 24 MiB after the auxiliary worker reserve; it
does not allocate artificial pressure or replace any arithmetic kernel.
Ranks that never create a handle keep their real memory report.

The previous implementation built a multi-GiB sparse density packet before
testing whether a GPU could hold it. A timed owner-thread backtrace found
vector growth in Builder::term -> SDG_recovery_visit -> bilinear_cost, while
the other MPI rank waited for collective recovery. The delayed-cap run did
not finish within 150 seconds. This was excessive host packing, not a
demonstrated MPI deadlock.

The new packer checks header/row metadata before visiting rows, then bounds
terms, unique orbitals and matrix data by the receiver's actual remaining
room. It stops without publishing a partial packet. A failed equal/smaller
budget is cached within the call; a larger GPU or smaller shard can retry.
The separate host-memory guard remains active. Remote source packets still
use the host guard; the receiving node applies the device limit locally.

All eight final Si64 runs pass energy-component and force comparisons:
  workers off, 1 SCF step: CPU recovery completes in 71.86 / 101.32 s;
  workers auto, 2 SCF steps: recovery completes in 101.20 / 176.00 s.
These are elapsed process times including MPI startup. The default-auto
pair has max energy difference 8.51e-11 Ha, force difference 2.36e-10
Ha/bohr, and energy-component difference 5.22e-9 Ha (tolerance 1e-7).
The cap also sends integral/force work to CPU, so these are recovery tests,
not low-memory performance predictions. Logs and summaries:
  capacity-debug/bounded-capacity/
  capacity-debug/bounded-capacity-auto/

A separate Si8 collinear/noncollinear test forces the sparse density GPU
path, with enough real memory and no interposer. Both GPUs execute the
bounded packets; energy/force differences are at most 1.01e-12.
Results: capacity-debug/density-gpu/summary.json.

Capacity hierarchy and remaining validation
-------------------------------------------
The default Cluster selector already implements:
  fitting owner GPU -> local MAGMA/custom GEMM -> distributed ELPA/COSMA
  (multi-node only) -> CPU.
A one-GPU-per-node pool skips local MAGMA. scf.Gpu.Num remains a per-node
upper bound. gpusolver3 forces the local MAGMA family and does not opt into
ELPA/COSMA. Explicit gpusolver2 selects the distributed family directly.
No automatic ELPA/COSMA test is used on one physical node.

PBS 943417 verifies the default gpusolver -> local MAGMA transition on two
real A100s, for Si64 collinear and noncollinear Cluster. A 65536 MiB native
cuSOLVER reserve triggers admission failure while MAGMA uses its real
memory budget. Both runs require the automatic-transition banner, valid
MAGMA solves and custom multi-GPU GEMM, and reject any ELPA solve. Against
the same candidate's native path, energy differences are <=9.67e-13 Ha and
force differences <=2.01e-12 Ha/bohr. Results:
capacity-debug/automatic-local-magma/summary.json.

The prepared physical two-node tests separately require:
  - default cuSOLVER admission failure -> local MAGMA;
  - local MAGMA memory admission failure -> GPU ELPA and COSMA;
  - one visible GPU per node -> directly distributed GPU execution;
  - four visible GPUs with scf.Gpu.Num=1 -> the same capped transition;
  - failure of every GPU tier -> completed CPU SCF/forces.
They record physical rank placement, selector diagnostics, backend profiles,
energy components, coordinates and forces. Test-only cudaMemGetInfo capping
does not allocate pressure or substitute GPU kernels. Reserve/tile overrides
used to force a transition are routing tests, not realistic capacity timings.
OPENMX_GS2_PROFILE records the grid root's complete call time, not an MPI
maximum or independent proof of COSMA's internal kernel choices.

Band's existing local cooperative pool rejects multi-node runs; its automatic
ELPA/COSMA fallback is not connected. Cluster policy results must not be
generalized to Band. Late MAGMA resource failures after successful admission
currently recover with CPU LAPACK, rather than re-entering the distributed
layout. These limitations are separate from the preflight hierarchy above.

Failed pre-fix attempts and diagnostic stacks are retained in shared-two/
device-capacity-cpu/, shared-two-capacity/ and capacity-debug/stack-capacity/.
The diagnostic stack stage intentionally times out. The allocation's zero
PBS exit status alone is not a test-suite pass; inspect each stage and the
final per-comparison summaries rather than treating that stage as a pass.
