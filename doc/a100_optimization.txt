OpenMX 4.0 GPU: A100 policy and validation
2026-10-12

Scope
-----
The GPU paths now select arithmetic from the actual device's FP32:FP64
throughput ratio rather than assuming that every NVIDIA GPU resembles a
GeForce. A100 reports 2. A known positive ratio below 8 selects native FP64
for general GEMMul8 bridge calls and, on newer toolkits, cuSOLVER math. GeForce retains
GEMMul8 and its existing compensated double-float/refinement fast paths.

Large real square fixed-forward transforms have a separately measured A100
exception: full sm_80 devices with at least 100 SMs may use unblocked GEMMul8
at n >=6144. Smaller transforms use native FP64. This does not apply to
complex or general products, H100, GeForce, A30 or smaller MIG partitions.
Automatic full-workspace allocation obeys free-memory/reserve checks; an
explicit workspace-fraction limit also applies. Allocation/query/budget
failure returns directly to native FP64, never to capped GEMMul8. The
general default's 30%-divided-by-local-ranks cap is not imposed on this
forward stage: collinear cluster diagonalization has one owner per spin,
while the other MPI ranks participate in grid work. This follows the
existing forward scratch lifetime and avoids counting all grid ranks as
simultaneous dense solvers. Explicit GeForce/forward selections are unchanged.

Native FP64 GEMM lets cuBLAS use A100 FP64 Tensor Cores without integer
decomposition or the GEMMul8 workspace. The new CUDA FP64 density kernel
tiles overlap points, stages each pair's density matrix in shared memory,
and preserves original grid indices when compact orbital tiles are used.
Unsupported dimensions/resources return to the existing OpenACC kernel.
Both paths retain FP64 accumulation. Orbital tile storage is unchanged.

On-the-fly orbital evaluation now follows the existing grid precision
device boundary: FP64 on A100, double-float on GeForce. Lossy FP32 grid
arithmetic remains an explicit experiment, disabled by default. FP32
eigensolver refinement already stayed disabled by default on A100; the
selection is now reported when verbose output is enabled.

On cuSOLVER versions with FP64 emulation, native A100 handles also avoid
the n-by-n backup and extra workspace queries used to recover from an
emulated solve's nonconvergence. This specific optimization cannot be
timed with the installed CUDA 12.5/cuSOLVER 11.6.3: those versions do not
provide the emulation API and were already using native solver math.

Controls
--------
scf.gemmul8.enable absent: automatic device selection.
scf.gemmul8.enable off: force native cuBLAS, including forward products.
scf.gemmul8.enable on: permit GEMMul8 on A100 as well as GeForce; environment
  disables still apply. This reproduces the earlier GEMMul8-on selection.

GEMMul8 disable controls have the following precedence, highest first:
  input-file off (absolute)
  OPENMX_GEMMUL8_DISABLE_D or OPENMX_GEMMUL8_DISABLE_Z
  GEMMUL8_DISABLE_D or GEMMUL8_DISABLE_Z
  OPENMX_GEMMUL8_DISABLE
  GEMMUL8_DISABLE
  explicit input-file on, then automatic device policy
For these environment variables, 1 disables and an explicit 0 enables
GEMMul8. Empty values do not override the next setting. Device detection
failure keeps the previous GEMMul8 default. Explicit forward experiments
(OPENMX_GEMMUL8_FORWARD=fp64|gemmul8 and its existing precision/reuse knobs)
keep their separate selection; an input-file off remains absolute.

OPENMX_ORBS_EVAL_PRECISION=fp64|df selects orbital evaluation arithmetic.
OPENMX_GEMMUL8_A100_FORWARD_MIN_N sets the automatic real square forward
  crossover (default 6144); 0 disables the exception. Explicit input on/off,
  D/global disable-environment choices, and forward-stage choices win.
  OPENMX_GEMMUL8_FORWARD_UNBLOCKED=0 also disables this automatic exception
  when reuse is off. Existing FORWARD_REUSE=1 implies unblocked execution
  and takes precedence over FORWARD_UNBLOCKED=0.
OPENMX_GRID_PRECISION=fp64|df selects grid quadrature arithmetic.
OPENMX_SETDEN_FP64_CUDA=0 selects native-density OpenACC for comparison;
  unset or 1 permits the new CUDA kernel, with resource-based fallback.
OPENMX_SETDEN_FP64_SPLIT_SPIN=0|1 overrides native CUDA density scheduling.
  Automatic scheduling splits spins when max_no > 32 and spin_count > 1,
  reducing shared-memory pressure. Smaller orbital tiers remain unsplit.
OPENMX_GRID_FP32 is still off by default.
OPENMX_EIGEN_REFINE=0 disables refinement; a positive integer explicitly
  requests that many refinement iterations, including on A100.
OPENMX_CUSOLVER_EMULATION=0|1 explicitly selects native/emulated solver
  math where supported. Unknown-device probing preserves the previous
  emulation default. CUDA 12.5 has no such emulation mode.
OPENMX_CUSOLVER_ALGORITHM retains its existing behavior: on CUDA 13.4
  Update 1/cuSOLVER 12.3.4+, auto delegates full spectra to the library's
  architecture/size/math-mode selector and preserves subset SYEVDX.
  Older toolkits retain their compatible SYEVD/SYEVDX implementation.
OPENMX_CUSOLVER_CACHE_MB still defaults to 64 MiB per rank. No unmeasured
  increase was made to memory retained by many ranks sharing an A100.

----------------------------------------------

was copied with scf.maxIter=8 and stdout=2. These are fixed eight-step runs,
not claims of converged observables. Resident Hamiltonian storage was off,

Large-orbital density scheduling
-------------------------------
The matched 50-repeat resident benchmark compared the same native FP64
kernel with all spins in one block versus one block per spin. At 48
orbitals, two spins improved from 0.556235 to 0.473932 ms, and four spins
from 1.598186 to 0.914475 ms. Four-spin shared storage falls from 72 to
18 KiB, allowing more active blocks. Both modes passed all 78 numerical
cases; split mode also passed compute-sanitizer with zero errors.
At 26 orbitals/two spins it was slightly slower (0.128197 to 0.133893 ms),
so the smaller tiers retain their original scheduling. These are resident
kernel/API measurements, not full SCF speedups. Logs: grid-split-0.log,
grid-split-1.log and grid-split-memcheck.log in the validation directory.
tests/run_setden_fp64_policy_cpu.py checks 23 boundary/override cases.

MPI scheduling and persistent band buffers
-----------------------------------------
Job 935926 compared eight fixed-step runs (eight MPI ranks sharing one
A100 under MPS), using B2C62_Band, ZrB2_2x2 and GGFF. Input copies fixed
geometry and eight SCF steps; this is not a convergence test. Existing
serial=1/persistent=0 defaults were compared with serial=0 and, for the
collinear cases, persistent=1. All five comparisons passed: maximum
eight-step electronic-energy difference 3.013e-12 Ha, final total-energy
difference 1.137e-12 Ha and force-component difference 1e-12 Ha/bohr.

ZrB2_2x2 exercised these controls with five dense owners among eight MPI
ranks. Turning serialization off increased its diagonalization phase from
3.376 to 3.543 s. Keeping serialized turns and setting
OPENMX_BAND_GPU_PERSISTENT=1 shortened diagonalization to 2.836 s, while
total wall time changed from 38.162 to 37.528 s (about 1.7%). Persistence
reduced context/cache transfer and release work, as confirmed by BANDPROF.

B2C62_Band and GGFF took the multiple-k-points-per-owner branch, which
already groups work and bypasses those controls; their nearly unchanged
timings do not support a scheduling-policy conclusion. The defaults are
therefore retained. Persistent buffers remain an opt-in for similar A100
workloads with sufficient memory; their current per-rank free-memory test
does not reserve aggregate standing storage for future dense owners.
Enabling persistence for every A100 job from this small-footprint example
would be unjustified. Logs, per-step energy checks and profile CSV:
work/codex_a100_20261012/band_policy/runs/.
