GPU capacity recovery outside the generalized eigenproblem
==========================================================

The default policy is capacity based. An existing GPU operation first uses
its rank's GPU. If that operation's buffers do not fit, it tries the allowed
GPUs on the same node. If the local node still cannot hold the work, ranks
at the same calculation phase cooperate across nodes. If no GPU layout is
admitted, the operation completes on the CPU. CUDA allocation failures before
publication follow the same recovery path. GPU memory exhaustion alone is
not a reason to terminate a calculation.
If an allocation fails after a successful capacity query, private buffers
are released and other local group sizes are tried before remote recovery.

This policy also applies with one GPU per node. With several GPUs per node,
local cooperation precedes communication with other nodes. CPU-only physics
branches remain on the CPU. Dense transforms whose operands and result are
already resident need no additional full matrix and retain their owner GPU.
The dense eigensolver/GEMM ladder is described in cluster_mgpu.txt.

On a multi-node Cluster run, the dense capacity order is still the owner's
GPU, MAGMA plus the custom tiled products on rank 0's local node, then
ELPA/COSMA over the distributed MPI grid, and finally CPU work. A one-GPU
node has no local MAGMA group and proceeds directly to the distributed
tier. Explicit gpusolver2 selection bypasses this automatic ladder;
gpusolver3 requests local MAGMA and does not opt into ELPA/COSMA.

Sparse density recovery bounds packet construction by the candidate GPU's
current free space, after the worker reserve and output storage. It rejects
oversized row metadata before visiting any orbital terms and stops packing
as soon as deduplicated inputs exceed that limit. A rejected packet may be
retried on a larger GPU or with a smaller shard; completed packets retain
their exact size and numerical contents. This avoids constructing many GiB
on the host only to reject a GPU with a few MiB available. The independent
host-memory guard still applies, and failed packing publishes no output.

Limits and controls
-------------------
CUDA_VISIBLE_DEVICES, scf.Gpu.Num and OPENMX_MGPU_NUM_GPUS bound each node's
pool. GPU ordinals are local to the node; the MPI protocol transfers values,
never another process's pointers or CUDA ordinals. scf.mgpu.enable=off or
OPENMX_MGPU=0 disables borrowing. No recovery path expands the configured
GPU limit. Auxiliary work keeps its node pool when ELPA/COSMA is selected
or no cooperative k-point group exists. Scheduler-provided visibility must
be preserved.

OPENMX_GPU_WORKERS:
  unset or auto : use additional GPUs only for capacity recovery (default)
  1 or on       : prefer a larger local group even when one GPU fits
  0 or off      : retain the owner GPU, then use CPU recovery
The forced performance splitter remains optional. It can be slower for small
operations; the historical measurements in gpu_workers_validation.txt are
not measurements of the new default capacity policy.

Band density work observes the active k-point group. Cooperative dense work
uses floor(G/K) GPUs per computed k-point only when that quotient is at least
two: K=3/G=4 has no cooperative group and K=3/G=8 uses six GPUs. Auxiliary
atom/grid work uses the node pool within the same input limit.
On multiple nodes, density recovery uses each helper's allowed node pool;
Cluster spin worlds and uneven Band k-point turns synchronize their recovery
phases over the calculation communicator so an idle group can help another.

Existing per-operation controls still decide whether to use a GPU kernel at
all. In particular, OPENMX_OLPKIN_RADIAL_GPU=1 retains its opt-in meaning;
that kernel's MPI capacity phases run with one OpenMP thread per rank.
OPENMX_GPU_WORKER_COPY=1 disables peer views for transfer testing.
OPENMX_MGPU_VERBOSE=1 reports admitted device lists; remote recovery also
reports the number of participating nodes and completion status.
OPENMX_GPU_CAPACITY_TEST_RECOVERY=1 is a regression-test control: bypass
legacy resident fast paths and enter the ordinary recovery planner. It does
not enlarge the GPU pool or change numerical precision.

Operations and data placement
-----------------------------
Recovery phases cover orbital grid tables, overlap grid lists, nonlocal/VNA
radial integrals and projector contractions, Hamiltonian base/quadrature,
density and XC grids, supported GPU energy/dipole terms, force contractions
and reductions, residual-history mixing, and sparse DM/EDM extraction.
The existing scalar-relativistic force kernels keep their physics eligibility
checks; spin-orbit branches that were CPU-only are not converted to GPU.

Point/pair/atom work is packed into bounded ranges. Ragged lists carry their
own offsets, so helpers do not require local copies of the originating
rank's neighbor tables. Projector and eigenvector recovery stages only the
rows required by each range. Density-grid contractions deduplicate orbital
and density-matrix blocks within each packet. XC ranges include the required
halos. Mixing history can remain on the host while Gram products and linear
combinations use GPU ranges. Original GeForce and A100 precision choices
are retained.

All ranks enter a recovery phase, including ranks with empty work and ranks
whose own operation has finished. A private MPI communicator isolates the
messages; only the MPI calling thread communicates. One helper rank per
node can use that node's allowed GPU pool. Failed helpers are removed and
work is repartitioned before falling back to the originating rank's CPU.

Allocation, publication and lifetime
-----------------------------------
The planner includes operands, outputs and scratch, keeps device headroom,
and admits heterogeneous free-memory layouts. UUID-ordered interprocess
locks serialize overlapping GPU groups without changing MPI rank binding.
Inputs and outputs for a GPU attempt are private until every piece succeeds.
Remote transfers acknowledge host allocation before sending large packets.
A failed attempt therefore cannot double-add forces, densities or energies.
CPU range scratch is bounded too; a host-memory shortage is reported rather
than silently exceeding host limits. Corrupt metadata, numerical solver
failure, and device errors during publication remain errors.

CUDA/OpenACC device binding and dense scope are restored after every worker.
The capacity implementation does not require MPI_THREAD_MULTIPLE, CUDA-aware
MPI, or peer access between nodes. Single-node peer access remains useful;
ordinary copies are used when it is unavailable.

Four-mode SCF/force comparison on allocated GPUs:
  python3 tests/run_gpu_workers_regression.py --baseline /path/to/baseline \
    --binary /path/to/candidate --output /new/output/path --gpus 4 \
    --workers-mode auto
Use --candidate-env OPENMX_GPU_CAPACITY_TEST_RECOVERY=1 to exercise recovery
adapters against a baseline that keeps its ordinary execution paths,
and --workers-mode 1 with --require-work NAME to check a specific distributed
phase. The tests record binary/input hashes, energies, components, forces
and device ownership. tests/gpu_task_mpi_check.c checks the actual CUDA/MPI
ladder, including occupied owners and GPU caps. Its --logical-nodes mode
uses disjoint GPU pairs on one physical node to test the wire protocol;
it is not a substitute for a physical multi-node run.
Link this check with -Wl,--wrap=cudaMalloc to enable the late-allocation test.
Its --local mode needs one MPI rank and two GPUs and checks the local/CPU
tiers, including a late allocation failure after successful admission.
--logical-single uses two ranks and disjoint single GPUs to test recovery
when each node is permitted only one GPU.

Build the actual CUDA/OpenACC MPI fixture with an NVHPC-backed mpicc:
  CUDA_HOME=/path/to/cuda CUDA_MATH_ROOT=/path/to/math GPU_ARCH=80 \
    bash tests/run_gpu_task_mpi_check.sh /path/to/test-build --build-only
On two allocated physical nodes, run one rank per node:
  mpirun -np 2 --map-by ppr:1:node /path/to/test-build/gpu_task_mpi_check
Each rank needs at least two visible GPUs for the full local/remote ladder.
Use --single-gpu-per-node for the actual one-GPU-per-node case. Unlike the
logical-node modes, it verifies each rank is alone on its physical node and
does not substitute simulated MPI shared-memory groups.

run_gpu_workers_regression.py accepts --ranks-per-node to request and verify
physical placement, --mpi-arg for launcher options, and --rank-wrapper for a
site's per-node GPU visibility/MPS setup. --candidate-input allows numerical
comparisons between different eigensolver selectors on the same geometry.
The results include application phase timings and a separate placement.json;
--require-remote-work NAME rejects a run that did not execute that remote phase.
--expect-candidate-backend magma/gs2-gpu/gs2-cpu checks actual dense dispatch;
the GS2 assertions require OPENMX_GS2_PROFILE=1. --require-candidate-log TEXT
can require the admission diagnostic as well, so a numerical pass cannot
mistake a directly selected backend for an automatic capacity transition.

tests/gpu_capacity_limit.c is a test-only LD_PRELOAD library which caps
cudaMemGetInfo's reported free memory with OPENMX_TEST_GPU_FREE_MB. It never
allocates artificial pressure or increases the reported free memory. This
permits testing a failed local MAGMA admission followed by real distributed
ELPA/COSMA kernels on allocated GPUs. Record the cap and any GS2 reserve/tile
overrides; such a run tests routing and accuracy, not memory-use performance.
OPENMX_TEST_GPU_FREE_AFTER_SOLVER=1 delays the cap until each rank first
creates a cuSOLVER handle, avoiding unrelated early integral capacity paths.

The 2026-10-16 build, numerical comparisons, fault-injection checks and
physical multi-node validation limits are recorded in gpu_capacity_validation.txt.
