PROVENANCE NOTE (hand-written; read before quoting anything above)
----------------------------------------------------------------------
1. Two campaigns ran today.  The first used the previous binary
   (f5fb5b3 + bundled GEMMul8 v3.1.1); after 12 probes the user ordered
   git pull (-> cd5f0d5, GEMMul8 v3.2.0), rebuild, and a full re-measure.
   The v3.1.1-era case dirs are quarantined in siband_v311_superseded/
   and are NOT in the table above.  Where both binaries completed the
   same cuBLAS probe, Utot is bitwise identical (col216, nc216, nc250;
   see Utot cross-checks) -- expected, since cd5f0d5 touches only the
   GEMMul8 build pin.  NOTE: `make` does NOT re-checkout GEMMul8 when
   the pin changes (target is the existing third_party/GEMMul8/Makefile);
   the v3.2.0 build required a manual checkout + rm of the stale .o/.a.
2. Toolchain: NVHPC 26.5 / CUDA 13.2 at runtime (plan 3.1 satisfied).
   Plan 3.1 pins "current main = 353b01f...", which exists in no local
   or remote history; actual GitHub main at measurement time = cd5f0d5.
   The paper's v2.0_thesis tag does not exist yet, so everything here
   is PREFLIGHT (GO/NO-GO + size selection), to be re-measured from the
   tag for production tables.
3. Probes are single samples; their wall times are never a ranking
   (site convention).  Only the 3-rep scaling series ranks backends.
4. Monotonicity of RSS vs atom count is broken by cell family: conv
   (cubic 8-atom) supercells carry much higher node RSS than prim (fcc
   2-atom) supercells of MORE atoms -- col288(conv)=107 GiB FAILs while
   col300/col360(prim)=76/82 GiB PASS.  The plan's boundary-adjacency
   re-check (7.3.1) is what caught this; a pure index bisection under a
   monotonicity assumption would have returned col=250 or worse.
5. Run-to-run RSS swing: col288 measured 99 GiB (v3.1.1 run) and
   107 GiB (v3.2.0 run) on identical solver code -- ~8 GiB spread on a
   124-GiB node.  This is why the 102-GiB (80%) gate exists and why
   near-gate passes are treated as fails.
6. 3-SCF probes under-estimate 25-SCF RSS: nc250 went 99 -> 104 GiB
   (rmm-diisk history=7 fills only after iteration ~8).  This is why
   plan step 6 (25-SCF confirmation) is mandatory; it demoted nc250,
   and NC stepped down to 216 per "1候補下げて再検証".
7. GEMMul8 host-memory cost is mode-asymmetric and decided col's size:
   col300 +17 GiB (76->93), col360 +23 GiB (82->105, gate FAIL ->
   step-down 360->300 per plan step 5); NC +0..1 GiB (nc216 99->99,
   nc250 99->100).  Hypothesis only: the device concurrency ladder cuts
   NC much deeper under GEMMul8 (nc216 8->4, nc250 7->3 turns vs col300
   8->7), so fewer per-rank workspaces exist at once; col360 cuBLAS-only
   remains feasible (25-SCF: 84 GiB) but the representative must carry
   BOTH backends.  Consequence worth reporting under RQ6: on a 128-GB
   host, enabling GEMMul8 shrinks the largest safe col-band system from
   360 to 300 atoms while leaving NC unchanged.
8. Fixed-iteration caveat: with the template's scf.criterion 1e-13,
   nc250_o CONVERGED at SCF=24, so 25-SCF wall times are not guaranteed
   comparable across configs.  The scaling-series decks pin
   scf.criterion 1e-15 (documented deviation from sidia.dat) so every
   run does exactly 25 iterations.  All four confirmation runs of the
   chosen representatives did complete SCF=25 under 1e-13.
9. Forces: ideal diamond, every atom on a symmetry site -> exact forces
   are zero; the MD.Type Opt / MD.maxIter 1 step runs (force code is
   exercised) but the force column cannot discriminate backends.  Utot
   is the accuracy check: cuBLAS vs GEMMul8 at 25 SCF differs by 1 ulp
   (col300: ...501012 vs ...501011) or matches bitwise (3-SCF nc216,
   col300 probes).
10. GPU engagement: every PASS row shows the <Band_DFT_Col/NonCol> GPU
   device banner with 8 k-owner ranks and 100% peak utilisation; zero
   "cannot fit" fallbacks anywhere in the campaign.  Multi-node
   preflights confirm the owner map thins as 8/4/2 k per GPU at 1/2/4
   nodes (plan 7.4).
