PROVENANCE NOTE 2 (2026-08-15): the gpusolver2 (d) columns
----------------------------------------------------------
Added scf.eigen.lib=gpusolver2 -- distributed multi-GPU cluster
diagonalization (ELPA 2026.02 with NVIDIA GPU kernels + COSMA), new in the
merge that this file's binary comes from.  The g/o/c columns are unchanged
measurements from the round-3 binary (e227507); the d columns were measured
on the gpusolver2-merge binary (f5fb5b3).  Both binaries reproduce the same
Utot per node count, so the columns are comparable.

  * The 1-node d point is 16 ranks/node, not 36.  gpusolver2 cannot run at
    36 ranks/node on these 124-GiB hosts: the 48-, 36- and 24-rank attempts
    were all OOM-killed (the 24-rank one got through the first solve and
    died in the DM build; plain gpusolver already peaks at 111/124 there).
    16 ranks/node completes at 115-116/124.  Read that one point as "the
    largest 1-node configuration that runs", not as a rank-matched
    comparison.
  * The 4-node d triple is d2/d3/d8 -- the first three reps whose FULL node
    set was free of bnode013 and bnode033.  Multi-node runs are screened on
    every node of the allocation here (the .env "=== nodes ===" list), not
    just the node the batch script happens to start on.  Discarded: d1, d4,
    d5, d7 (bnode013), d6, d7 (bnode033).  d9 was clean but surplus.
  * Observation worth keeping: in this 4-node GPU configuration bnode013 is
    NOT measurably slow (278.2-282.5 s on it vs 279.0-282.6 s clean), while
    bnode033 is (293.7-303.5 s, +5-8%).  The slow-node screening still
    discarded both, per standing convention.
  * Caveat on the pre-existing data: s443nc_4n_o3 (139.077 s), measured in
    the earlier campaign when only the head node was checked, ran on a set
    that included bnode013.  It sits inside the spread of its own triple
    (135.40 +- 3.24) and bnode013 shows no slowdown in 4-node GPU runs, so
    the 4-node g8-off mean above is left as measured rather than re-run.

Result: gpusolver2 is 1.5-1.8x faster than the CPU path but 2.1-3.6x slower
than plain gpusolver (single-rank cuSOLVER) at every node count.  Its
Diagonalization is the only one of the three that scales with node count
(566 s at 1n16 -> 325 -> 274 -> 240 s), because it is the only distributed
diagonalization here; gpusolver pins the whole solve to one H100 and sits
flat at ~91-94 s, which n=9984 is still small enough to win with.  Two
tuning attempts were measured and rejected: restricting the eigensolve to a
sub-grid of fewer ranks (1 rank/GPU was 2.4x slower than all 36; the
optimum is the full grid) and the ELPA 1-stage solver (1.5x slower AND a
300x worse SCF residual at iteration 25).  gpusolver2's value here is
reach, not speed: it is the path for systems too large for one GPU.
