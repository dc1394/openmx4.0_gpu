dia64dc_1n48_{g,o,c}1 and asserts 22 fields per case, including MD.Type=Opt
and MD.maxIter=1 -- the generator refuses to emit anything if the deck is not
doing the single optimisation step that produces forces, since that omission
is what invalidated the previous attempt.  All 36 cases: 792 PASS / 0 FAIL.

Jobs 913066..913121 plus 913097 (the o4 replacement), submitted 2026-08-16 in
three waves, queue gen_S, account GPU2026.  Each wave was one repetition of
all 12 (node count, config) points, 12-13 jobs at a time rather than all 36 at
once: the earlier 33-job burst on this machine put ~25 s of shared-filesystem
contention into Total, which matters more here where the fastest runs are
under 70 s.  Submitting a whole repetition per wave also means any residual
contention hits all three configs symmetrically instead of biasing one.

is >= 800 (Divide_Conquer_LNO.c, OPENMX_DCLNO_GPU_THRESHOLD).  Had this system
fallen below that, all three configs would have run the same CPU eigensolver
and the g/o/c spread would have been noise.  It did not: every g and o run
shows the "(GPU-accelerated)" banner and 100% peak GPU utilisation, with
28.6-58.3 GiB of device memory in use.  The comparison is real.

What the ranks are actually doing
----------------------------------
Set_Allocate_Atom2CPU.c caps atom-owning ranks at min(numprocs, atomnum), and
this system has 64 atoms.  So 1 node has 48 owners and 2, 3 and 4 nodes all
have 64 -- the 96, 144 and 192 ranks launched at 2/3/4 nodes perform the same
64 cluster solves.  Solver==11 (DC-LNO) additionally takes the ID2ID spreading
remap at Set_Allocate_Atom2CPU.c:333, which distributes those owners across
the nodes instead of packing them onto the first ones.

That cap does NOT flatten the curve, and it was wrong to expect it would:
CPU Diagonalization runs 570.3 / 275.2 / 211.8 / 184.2 s over 1-4 nodes, a
3.10x gain.  Spreading 64 owners over more nodes drops the per-node owner
count from 48 to 16, so each owner gets more memory bandwidth and cache, and
on the GPU path more devices.  The scaling is real but its mechanism is
thinner packing, not more parallelism -- which is why it decays toward the
node count rather than tracking it, and why a larger system would scale
differently.

GEMMul8 is a small net loss on this workload
---------------------------------------------
gemmul8-on is 1.01-1.02x SLOWER than plain cuBLAS at every node count, in
both Total and Diagonalization, and the effect is larger than the run-to-run
SD at 1, 3 and 4 nodes.  The reason is structural: GEMMul8 intercepts only
the three DGEMM calls per cluster solve in DCLNO_Solve_Col_GpuSolver, while
the cusolverDn eigendecomposition sitting between them -- the dominant cost --
is untouched.  A per-call overhead spread over three GEMMs of dimension ~832
has nothing large enough to amortise against.  Contrast the s443nc cluster
solver, where on and off were indistinguishable.
Utot is bit-identical between on and off at every node count, so this is
purely a speed question with no accuracy trade to weigh against it.

Verification
------------
Utot bit-identical across the three reps of all 12 points.  gemmul8-on and
gemmul8-off agree bit-for-bit with each other; elpa2 differs from both by
7.1e-11 Hartree on a total of -373.46, i.e. the 13th significant digit.

|Maximum force| is reported but does not discriminate here.  MD.Type Opt now
produces the MD table, and it reads 0.00000000 at 8 dp for all 36 runs; the
12-dp recomputation gives 2.4-2.5e-11 (GPU) and 3.7e-11 (CPU).  This is not a
harness limitation -- the deck is ideal diamond with every atom on a symmetry
site, so the exact forces are zero and what is tabulated is roundoff.  To get
forces that separate the solver paths the structure has to be displaced off
its symmetry sites.  Utot remains the accuracy check that actually bites.

Host memory is not a constraint at any point measured: 26-55 GiB of 124.
